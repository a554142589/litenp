# Benchmark Methodology

`litenp` benchmarks are meant to show two different performance stories:

1. Structure-aware lazy semantics can avoid work for arrays with known structure.
2. Materialized dense kernels can be competitive for common CPU array operations.

Those are not the same claim. The report keeps both because both matter, but row
names and documentation must make the distinction explicit.

## Categories

The benchmark is split into three groups, emitted in order by
`benchmarks/bench_litenp.cpp` (and mirrored row-for-row by
`benchmarks/bench_numpy.py`) under `=== group: ... ===` banners. The split is
by *input data character*, because that is what determines whether litenp's
structure-aware fast paths can fire.

### Group 1 — Structured

Rows in the `structured` group run over uniform / metadata-only inputs: `ones`,
`full`, `eye`, `transpose uniform metadata`, `sum uniform ...`, and `matmul
uniform ...`. For example, `ones<float>({n})` records shape plus the value
`1`; it does not necessarily write `n` floats until a materializing API
requires storage. Likewise, reductions or matrix products over uniform inputs
may use algebraic shortcuts.

These rows measure the benefit of preserving structure. They should not be
read as generic dense memory bandwidth or generic GEMM throughput. Large
speedups here mean `litenp` avoided materialization or dense compute by
keeping semantic metadata — a real feature, but a different feature from a
faster dense kernel.

### Group 2 — Dense-Patterned

Rows in the `dense-patterned` group run over materialized buffers filled with
deterministic but non-uniform data, typically `idx % N` patterns (`unary`,
`condition` / `where` / `clip`). This defeats the uniform-value shortcut
while staying bit-for-bit reproducible across runs and machines, so it is
the cheapest way to exercise the generic materialized kernel without
structure-aware shortcuts firing.

Allocation-free `*_into` rows time preallocated output paths. Allocating API
rows include the cost of creating the result.

### Group 3 — Dense-Random

Rows in the `dense-random` group run over non-uniform random data generated by
a fixed-seed LCG (`add random`, `multiply noncontig`, `sum random`, `matmul
random {128,256,512,1024}`). This is the closest group to ordinary dense
workloads and is the group to read when comparing litenp dense kernels
against NumPy/Eigen/libtorch on realistic data. It also includes
**noncontiguous (strided) inputs** (`slice(..., step=2)`), which force the
generic strided kernel and defeat contiguous fast paths, and a multi-size
random matmul sweep that exposes the litenp GEMM vs BLAS gap without the
uniform-value algebraic shortcut masking it.

Dense-random rows are marked `required: false` in the manifest: they ship
performance evidence (litenp is not yet competitive with NumPy on random
reductions / GEMM) without gating the pass/fail report. They are the
"Current Gaps" rows made runnable.

## Baseline Comparisons

The benchmark manifest records which baselines are applicable for each row:

- NumPy baselines are generated by `benchmarks/bench_numpy.py`.
- Eigen and libtorch baselines are emitted by `benchmarks/bench_litenp.cpp` when
  those optional dependencies are available.
- A row with no meaningful equivalent baseline marks that baseline as disabled.

Thread-sensitive benchmark runs should pin library thread counts:

```bash
OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1
```

The benchmark does not pin CPU frequency, isolate cores, disable turbo, or claim
cross-machine reproducibility. Treat the numbers as single-machine evidence, not
as a universal ranking.

## Reading Speedups

Large speedups in structure-aware rows usually mean `litenp` avoided
materialization or dense compute by keeping semantic metadata. That is a real
feature, but it is a different feature from a faster dense kernel.

Dense kernel rows are better evidence for common materialized workloads. They
still depend on compiler flags, vector ISA, memory bandwidth, BLAS backend,
thread settings, and cache state.

## Naming Rules

Benchmark row names should identify special structure when it drives the result:

- Use `uniform` when inputs are all the same value (structured group).
- Use `random` when inputs are LCG-generated non-uniform data (dense-random group).
- Use `noncontig` when inputs are strided views that defeat contiguous fast paths.
- Use `metadata` when the output can remain virtual or structure-only.
- Use `*_into` for preallocated output kernels.
- Avoid names like `materialize` unless the row forces a real dense output.

## Current Gaps

The dense-random group (Group 3) closes most of the prior gaps: it already
ships random `sum(axis)` and `matmul` inputs, strided (noncontiguous)
materialization, and a multi-size random matmul sweep. Remaining useful
additions before any broad performance claim is made:

- dense transpose materialization on non-uniform data;
- randomized broadcasting with non-uniform rows and columns;
- random `mean`/`max` along an axis (not just full-reduction), to stress
  the axis-reduction kernel on non-uniform data.
